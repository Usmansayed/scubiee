# Scubiee on Kiro CLI — A/B results (c_ship vs without)

Runtime: **Kiro CLI** `kiro-cli chat` v2.23.1, headless (`--no-interactive --output-format
stream-json`), model `auto`. Auth via `KIRO_API_KEY` env var. Scubiee engine 0.3.140 (warm, dense).
Harness: `scripts/claude_sdk_harness/run_kiro_ab.py` (mirrors the Cursor harness — same SHA-identical
git-snapshot isolation, same hidden oracles, same oracle-based success grading, multi-turn via
`--resume-id`). **Cost unit is Kiro CREDITS** (`meteringUsage`), not raw tokens — Kiro does not emit
token counts, so cross-runtime absolute comparison with Cursor is not meaningful; the within-Kiro
ship-vs-without comparison is.

## Setup / isolation (all preflights passed before token spend)
- Kiro CLI headless works; `stream-json` emits `meteringUsage` (credits), `tool_call` events with
  `_meta.kiro.{toolName,mcpServerName}` (so Scubiee map calls are counted exactly), and
  `runFinished{status,finalText}`.
- Per-arm isolation via **Kiro agent configs** (`.kiro/agents/kab_*.json`), generated by
  `build_kiro_agents.py` from `cursor_rules.variant_text('c_ship')`:
  - `kab_ship` — dev-capable, **inline Scubiee v3 MCP** (`map_v3_server`, read-only locate:
    `CTX_AUTO_INDEX=0`/`CTX_BACKGROUND_SYNC=0`) + the **c_ship rule** (= c_default + the one strict
    line) as its system prompt; tools fs_read/fs_write/execute_bash/@scubiee/map|gate|status.
  - `kab_without` — native tools only, no MCP, neutral dev prompt.
  No user/global config is touched; the two arms differ ONLY in `--agent`.
- Oracle validity (fails-empty / passes-correct) was established for these tasks in the Cursor
  session; the ship-agent's live Scubiee `map` call was verified before the run.
- **Harness bug found & fixed during preflight:** on Windows the kiro-cli `.exe` spawns
  grandchildren (agent + MCP) that keep the stdout pipe open, so a plain `proc.kill()` deadlocked
  the reader (one `without` cell hung ~15 min). Fixed by detecting `runFinished` in the reader and
  killing the whole process tree with `taskkill /F /T`. After the fix the same cell completed in 100s.

## Result — `unify_token_estimate` (cross-module edit, vague prompt), n=4 per arm

| arm | credits (each) | avg | median | map calls | native ops | success |
|---|---|--:|--:|---|---|--:|
| **kab_ship** (Scubiee + c_ship) | 1.02, 1.17, 2.12, 7.10 | **2.85** | **2.12** | 1,1,1,1 | 1,1,4,4 | 3/4 |
| kab_without (native) | 3.36, 3.07, 4.83, 3.53 | 3.70 | 3.53 | 0,0,0,0 | 4,3,6,4 | 3/4 |

### Read
- **Scubiee is cheaper on Kiro for this task: ~23% lower avg credits (2.85 vs 3.70), ~40% lower
  median (2.12 vs 3.53).** The ship arm's best two reps (1.02, 1.17) are far below anything the
  native arm produced (min 3.07) — when the agent trusted the single `map` call it did ~1 native op
  and finished cheaply.
- **Scubiee adoption is reliable on Kiro: map called in 4/4 ship cells** (unlike Cursor, where
  c_default often called map 0 times). The Kiro agent-config `prompt` + `@scubiee/map` tool wiring
  makes the agent actually use map. Native ops are consistently lower in the ship arm (avg 2.5 vs
  4.25) — map is **substituting**, not supplementing, here.
- **Variance is still large** (ship r4 spiked to 7.10 when it did extra work). Correctness tied at
  3/4 each (one strict-oracle miss per arm — the agent made a valid-but-partial edit).

## How this compares to Cursor
- On Cursor, the SAME task (`unify_token_estimate`) was a **wash** (c_default ~214k tok vs without,
  overlapping) and Cursor's agent frequently **ignored map** (0 calls on edit tasks).
- On Kiro, Scubiee **adopts more reliably (4/4) and comes out ~23–40% cheaper** on this edit task.
  The likely reason: Kiro's agent-config binds the Scubiee tools + rule tightly into the agent's
  own context, so the host's native-tool bias is weaker than Cursor `auto`'s. This is the first
  edit-task arm where Scubiee shows a token/credit win rather than a wash.

## Caveats (honest)
- **Credits ≠ tokens.** This is Kiro's billing unit; do not compare the absolute numbers to Cursor's
  token totals. Only the within-Kiro ship-vs-without ratio is meaningful.
- n=4 per arm, model `auto` (non-deterministic) — the ~23–40% win is directional, not a tight CI.
  The spread (1.02 → 7.10 on ship) means a single spiky rep moves the mean a lot.
- Only one task type run so far (`unify_token_estimate`, a cross-module edit). The Cursor spectrum
  (retrieval = big win, feature build = no win) likely holds on Kiro too; retrieval/feature tasks
  are the next runs to confirm the shape.
- Both arms 3/4 success — rule choice changed cost/adoption, not correctness (consistent with the
  whole project's finding).
